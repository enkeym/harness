# ragsave — смысловой (RAG) слой поиска, парный к tokensave

tokensave отвечает на **структурные** вопросы о коде: где определён символ, кто
его вызывает, что сломается при правке. Он строит граф — и умеет только то, что
в граф попало.

ragsave отвечает на **смысловые** вопросы и по **всем** текстовым файлам
репозитория, включая те, которых в графе нет вовсе: документацию, json/yaml,
миграции, SQL, `.env.example`, CI-конфиги, комментарии. Вопрос «как настроен
деплой» или «где описаны переменные для почты» не сводится к имени символа —
на него отвечает ragsave.

Инструменты не конкурируют: один ищет по структуре, другой по смыслу.

## Как устроено

```
файл → чанки → эмбеддинг (ONNX, локально) → .ragsave/rag.db
                                              ├── vec_chunks  (векторы, sqlite-vec)
                                              └── fts_chunks  (слова, FTS5)
запрос ─┬→ вектор  → топ-N по близости ─┐
        └→ слова   → топ-N по BM25    ──┴→ слияние RRF → фрагменты с file:line
```

Гибридный поиск намеренный: чистый вектор не находит точные идентификаторы
(имя ключа в yaml), чистый BM25 не понимает переформулировок. Вместе они
закрывают слабости друг друга.

В оба индекса подмешивается путь файла. Причина практическая: у конфигов нет
прозы — `smtp: host: port:` плохо ложится в вектор, и запрос «настройки почты»
мимо такого файла проходит. Путь `config/mail.yaml` сообщает тему надёжнее
содержимого. Показывается при этом всегда чистый фрагмент.

Никаких серверов, демонов и Docker — один файл `.ragsave/rag.db` на проект,
рядом с `.tokensave/tokensave.db`. Эмбеддинги считаются **локально на CPU**:
код никуда не отправляется, API-ключи не нужны, работает офлайн.

### Состав

```
~/.rag-mcp/
├── venv/                 # изолированный python: fastembed, sqlite-vec, mcp
├── models/               # кеш ONNX-модели (~2.2GB, скачивается один раз)
└── ragsave/
    ├── config.py         # пути, модель, что считать текстовым файлом
    ├── embedder.py       # текст → вектор (ленивая загрузка модели)
    ├── chunker.py        # разбиение по смысловым границам
    ├── store.py          # SQLite + sqlite-vec + FTS5, гибридный поиск
    ├── indexer.py        # обход проекта, инкрементальность по sha256
    ├── server.py         # MCP-сервер (stdio)
    └── cli.py            # терминальный интерфейс

~/.local/bin/ragsave              # обёртка CLI
~/.ai-hooks/bin/ragsave-sync.sh   # автоиндексация на хуках агента
```

Модель по умолчанию — `intfloat/multilingual-e5-large` (1024 dim, 2.24GB):
лучшее качество среди multilingual в fastembed, уверенно держит русский.

## Использование из агента

Инструменты подключены как MCP-сервер `ragsave` и уже в allow-list — работают
без запроса подтверждения.

| Инструмент   | Зачем                                                        |
| ------------ | ------------------------------------------------------------ |
| `rag_search` | смысловой поиск по проекту, возвращает фрагменты с `file:line` |
| `rag_status` | что в индексе: файлы, фрагменты, модель, размер БД            |
| `rag_index`  | построить/обновить индекс вручную                             |

Параметры `rag_search`:

- `query` — запрос на естественном языке (обязательный);
- `limit` — сколько фрагментов вернуть, по умолчанию 8;
- `path_include` / `path_exclude` — фильтр по подстрокам пути, чтобы отсечь
  чужой стек (`["client/"]`, `["server/"]`);
- `only_outside_tokensave` — искать **только** там, куда tokensave не
  заглядывает: доки, конфиги, миграции;
- `project` — путь к проекту, если он не совпадает с текущим каталогом.

## Использование из терминала

```bash
ragsave init          # построить индекс (первый раз — минуты)
ragsave sync          # дособрать изменения (секунды)
ragsave status        # статистика индекса
ragsave reindex       # перестроить с нуля (после смены модели)

ragsave search "как настроен деплой"
ragsave search "переменные окружения почты" --outside   # только не-код
ragsave search "оплата" --include client/ -n 5
ragsave search "миграции" --json                        # машинный вывод
```

Все команды принимают путь к проекту вторым аргументом; без него берётся
текущий каталог, корень определяется через git.

`init`/`sync`/`reindex` рисуют однострочный прогресс-бар в stderr (перезапись
через `\r`, как у `pip`/`apt`):

```
[ragsave] [████████████████████░░░░░░░]  75% (6/8)  35с  эмбеддинг: 90/120 фрагментов
```

Список файлов собирается заранее, поэтому сразу известен знаменатель. Проход
идёт в две фазы: сначала сканирование (быстро добегает до доли файлов, которые
не изменились или восстановлены из кеша), затем эмбеддинг очереди — там доля
растёт дробно по фрагментам, а в детали видно `эмбеддинг: 90/120 фрагментов` и
текущий файл. Векторы приходят батчами (`RAGSAVE_BATCH`, по умолчанию 32),
поэтому бар обновляется раз в батч — на e5-large это десятки секунд, это не
зависание.

Флаг `--quiet` убирает весь вывод — им пользуется хук автоиндексации, чтобы не
засорять `sync.log`.

### Почему число файлов меньше, чем в git

Строка `файлов для индексации: N (из M в git; ...)` показывает разницу явно.
Основная причина — служебные каталоги (`SKIP_DIRS` в `config.py`): `node_modules`,
`dist`, `.cache`, `coverage` и т.п. не индексируются вовсе. `.cache` — самое
неочевидное совпадение: он рассчитан на кеши сборщиков (`.parcel-cache`,
`.turbo`), но так же называется и папка `<project>/.cache/`, где кто-то мог
хранить, например, кеш данных для бэктестов. Такие файлы отсекаются тем же
правилом — семантический поиск по числовым дампам всё равно бесполезен, но
если у вас есть каталог `.cache` с содержимым, которое хотелось бы искать,
переименуйте его или сообщите, чтобы уточнить список.

## Автоиндексация

`~/.ai-hooks/bin/ragsave-sync.sh` висит на двух хуках Claude Code:

- `SessionStart` — догоняет правки, сделанные между сессиями (терминал,
  `git pull`, другая ветка), пока идёт первый ход;
- `Stop` — по завершении ответа дособираются изменившиеся файлы.

Оба вызова уходят в фон и не задерживают агента. Синк без изменений не грузит
модель вообще — Embedder ленивый, а нетронутые файлы отсекаются по `stat`.
Индекс хук только обновляет: без `.ragsave/rag.db` он молчит, первичный
`ragsave init` запускает человек. `.ragsave-disable` в корне репозитория
выключает хук и для проекта с индексом.

Во время синка `rag_search` работает: БД в режиме WAL, синк пишет по файлу на
транзакцию. Пока файл не пересчитан, поиск отдаёт его прежнюю версию, новый
файл до эмбеддинга не находится.

`rag_search` помечен `_meta["anthropic/alwaysLoad"]`: без метки Claude Code
держит его в deferred за `ToolSearch`, а основные инструменты tokensave
загружены сразу — и модель выбирала их, даже когда вопрос был смысловой.

Замок на проект (`.ragsave/.sync.lock`, `flock`) берёт сам `ragsave`, а не
хук — поэтому он один для всех путей запуска: фоновый хук, ручной `ragsave
sync` из терминала, `rag_index` из MCP. Второй пришедший не ждёт занятую БД
и не падает с `database is locked`, а сразу выходит с кодом 3 и строкой
`another sync is already in progress (PID …, начат …)`; `log-error.sh` такую
запись отказом не считает. Ручному запуску можно велеть подождать:
`ragsave sync --wait 600`.

Раньше замок держал сам хук, и любой запуск мимо него (терминал, MCP) упирался
в БД, которую индексация держит открытой на запись, — отсюда и были
`sqlite3.OperationalError: database is locked` в `errors.log`.

Скрипт ничего не делает вне git-репозитория и в `$HOME`.

## Переключение веток

Индекс один на проект и хранит состояние рабочего каталога — то, что сейчас
лежит на диске. При смене ветки пересчитываются **только** файлы, чьё
содержимое реально отличается. Проверка двухступенчатая: файл с прежними
размером и mtime не открывается вовсе; файл, который checkout тронул, но
содержимое (sha256) прежнее, только получает новый mtime в индексе, чтобы в
следующий раз не хешироваться.

Сверх этого работает кеш по содержимому. Каждый посчитанный фрагмент
запоминается под хешем **содержимого файла**, а не его пути, поэтому:

- возврат на ветку, где вы уже были, восстанавливается из кеша, не обращаясь
  к модели вовсе;
- переименованный или скопированный файл с прежним содержимым тоже берётся из
  кеша;
- ветка без изменений в файлах не стоит ничего — модель не загружается.

Измерено на реальной модели, один изменённый файл:

```
первое переключение (нужен счёт)   9.95 с   ← из них ~10 с загрузка модели
возврат на прежнюю ветку           0.46 с   ← restored_from_cache: 1
```

Выигрыш тем заметнее, чем чаще прыгаете между ветками: модель весит 2.24 GB, и
не поднимать её в память — основная экономия.

Кеш чистится сам на каждом проходе: записи, не использованные 45 дней,
удаляются, и держится потолок в 20 000 версий файлов. Текущий объём виден в
`ragsave status` (`cache_versions`, `cache_chunks`), а в отчёте индексации —
поля `restored_from_cache` и `cache_pruned`.

Смена модели эмбеддингов сбрасывает кеш вместе с индексом: старые векторы
несовместимы с новыми, и переиспользовать их нельзя.

### Отключить индексацию отдельного проекта

```bash
touch /путь/к/проекту/.ragsave-disable
```

### Удалить индекс

```bash
rm -rf /путь/к/проекту/.ragsave
```

`.ragsave` добавлен в `~/.gitignore_global` — в репозиторий не попадёт.

## Когда какой инструмент

| Вопрос                                            | Инструмент                    |
| ------------------------------------------------- | ----------------------------- |
| Где определён `UserService`?                       | `tokensave_search`            |
| Кто вызывает `calculatePrice`?                     | `tokensave_callers`           |
| Что сломается, если поменять этот метод?           | `tokensave_impact`            |
| Как устроена авторизация в проекте?                | `tokensave_context`           |
| Как настроен CI/деплой?                            | `rag_search`                  |
| Где описаны переменные окружения для почты?        | `rag_search --outside`        |
| В каком конфиге лежит таймаут воркера?             | `rag_search`                  |
| Что говорит README про запуск локально?            | `rag_search`                  |
| Точное имя ключа в json-конфиге                    | `Grep` (быстрее и точнее)     |

Правило: **знаешь имя символа — tokensave; описываешь смысл словами — ragsave;
знаешь точную строку в неиндексируемом файле — Grep.**

## Смена модели

```bash
export RAGSAVE_MODEL="sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2"
ragsave reindex
```

Доступные варианты перечислены в `config.py` (`_MODELS`). Размерность вектора у
моделей разная, поэтому после смены индекс обязательно строится заново —
`ragsave search` сам откажется работать и подскажет это, если увидит
несовпадение.

## Скорость

Почти всё время индексации — модель на CPU; чтение, хеширование и запись в БД
на её фоне не видны. Поэтому «параллельная сборка файлов» сама по себе ничего
не даёт, и устроено так:

- сканирование (stat, чтение, sha256, чанкинг) идёт в отдельном потоке и
  перекрывается с записью в БД и восстановлением из кеша, но модели не ждёт;
- все фрагменты, которым нужна модель, уходят в неё **одним** потоком с
  батчами по `RAGSAVE_BATCH` (32): на e5-large батч 32 против 8 даёт вдвое
  больше фрагментов в секунду (0.69 против 0.34 на 22 ядрах), так как ONNX
  эффективнее на крупных матрицах;
- синк без изменений не читает файлы вовсе: неизменённые размер и mtime
  отсекают файл до открытия, sha256 считается только для тронутых.

Ручки (переменные окружения):

| Переменная         | Что делает                                                  |
| ------------------ | ----------------------------------------------------------- |
| `RAGSAVE_BATCH`    | фрагментов на вызов модели (32)                              |
| `RAGSAVE_PARALLEL` | процессов-воркеров модели; каждый держит свою копию (~3 GB) |
| `RAGSAVE_THREADS`  | потоков ONNX в одной инференции (по умолчанию решает ORT)   |

`RAGSAVE_PARALLEL` — data-parallel режим fastembed: пул процессов поднимается
на весь проход, каждый грузит модель заново. При 16 GB в WSL и MCP-сервере,
уже держащем одну копию, запас есть на 1–2 воркера; см. замеры ниже.

Настоящий рычаг — модель. `paraphrase-multilingual-MiniLM-L12-v2` (384 dim,
0.22 GB) считает на порядок быстрее e5-large при заметно худшем русском;
`paraphrase-multilingual-mpnet-base-v2` (768 dim) — компромисс. Смена — через
`RAGSAVE_MODEL` и `ragsave reindex`.

## Тесты

```bash
~/.rag-mcp/venv/bin/python ~/.rag-mcp/tests/test_ragsave.py   # ragsave: 80 проверок
node ~/.ai-hooks/test/test-guards.mjs                          # гарды: 150 проверок
```

Тесты ragsave не грузят модель — эмбеддер подменяется детерминированной
функцией, поэтому проверяется логика (чанкинг, инкрементальность, фильтры,
слияние результатов), а не качество векторов. Тесты гардов прогоняют каждый
сценарий через оба агента (Claude Code и OpenCode) и требуют совпадения
вердиктов.

## Диагностика

```bash
ragsave status                        # есть ли индекс, чем построен
cat ~/.ai-hooks/logs/errors.log       # отказы фоновых задач по всем проектам
cat /путь/к/проекту/.ragsave/sync.log # что делал фоновый синк в этом проекте
claude mcp list                       # видит ли Claude Code сервер
```

`~/.ai-hooks/logs/errors.log` — общий журнал отказов tokensave и ragsave.
Фоновые индексации уходят в `setsid` и молчат: упавшую задачу иначе можно
заметить, только зная заранее, в какой лог смотреть. Формат —
`[время] источник | проект | exit=код` и хвост лога задачи. Ротация при 5 МБ.

Туда пишут `ragsave-sync.sh` и MCP-сервер ragsave —
последний только на неожиданных исключениях: штатные отказы вроде «индекс не
построен» лог не засоряют. Пустой файл тоже говорит о многом — значит фоновые
задачи не падали и причину стоит искать в другом месте.

Пустой результат поиска в свежем проекте обычно значит, что фоновая индексация
ещё идёт — проверьте `sync.log`.

`ragsave sync` вышел с кодом 3 и `another sync is already in progress (PID …)`
— проект в этот момент индексирует другой процесс (обычно фоновый хук). Это не
ошибка: подождите его или запустите с `--wait 600`. Кто именно держит замок,
записано в `.ragsave/.sync.lock`.

В отчёте индексации поле `embed_seconds` — чистое время модели: по нему видно,
стоит ли крутить `RAGSAVE_BATCH`/`RAGSAVE_PARALLEL` или менять модель.
