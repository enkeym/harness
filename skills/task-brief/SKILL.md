# task-brief

Load before substantive investigation or implementation when the task needs architectural decisions, module boundaries or contracts, coordinated changes across components, a complex audit, or debugging with uncertain causes, competing hypotheses or an unsuccessful approach. Explicit requests for a brief, plan, task analysis or design comparison also trigger this skill, even without implementation. Judge complexity by uncertainty, dependencies and consequences, not message length, keywords or file count alone.

Skip routine local changes with a known solution, factual explanations, mechanical commands and execution of an adequate existing plan. An ordinary review uses the review workflow; add this skill when it needs an investigation plan or architectural decisions. Reassess when new evidence invalidates the plan, requirements change materially, or diagnosis stalls; continue from recorded decisions instead of restarting the brief on every turn.

Keep small plans in the conversation. When a plan needs a file, use `.opencode/plans/<task-id>.md` under the project root, with a unique task identifier; an explicit user path takes precedence. Reuse the same path across continuation and record it in the handoff. Keep the plan while work is unfinished or blocked. After the task and its checks are complete, delete only this task's temporary plan before the final response; this cleanup is authorized as part of the task. Preserve user-owned plans and other tasks' files. Do not create a root `PLAN.md` or delete an existing root plan without verifying that it is this task's temporary artifact. Without a file, keep the same compact checkpoint in the conversation: open result, exact check and blocker reason, plus short evidence for closed results. Do not create a plan file or call the transition for a continuous short task, and use the same format after native compaction without a plan.

Load only the domain and stack skills for the code affected by the plan. In an indexed project inspect it through tokensave-routing: scoped search and small line ranges; use context without code only to locate unfamiliar structure. Without an index use local search and bounded reads. Reuse project decisions. State the goal, boundaries, assumptions, proposed steps and verification, scaled to the task. Ask only about unresolved choices that materially affect the result. Existing user authorization is sufficient to proceed; do not introduce an additional approval gate or implement changes when only analysis was requested. For a design choice, compare the strongest alternatives with evidence. Harness health diagnostics belong to doctor; it complements this workflow when that is the subject of analysis.

Make the plan executable: record relevant paths and contracts, chosen approach and reasons, unresolved hypotheses, ordered steps, acceptance checks and the next action. Separate verified facts from assumptions; a debugging plan starts with evidence and discriminating checks. Preserve user constraints and authorization through continuation.

When an implementation or post-fix review has a plan, read it line by line before starting work or transferring it. Turn every required outcome and every named check into a separate row in `## Acceptance criteria`, in the plan's order. Include boundary cases, check-only items, and requirements that need no code changes. For each row record the invariant, trigger or event order, expected observable result and exact check. In particular, keep cancellation, generation changes and deadlines on separate rows when each can invalidate an otherwise successful result. Before `implement`, check that the critical rows verify the confirmed requirement, contract or callers rather than restating the proposed code, and that no example or assumed cause became a baseline. A contradicting fact stops the affected step: show the original expectation, the fact and the correction, and change the agreed contract only with explicit confirmation; then reopen only the affected rows.

Use stable IDs and one line per row: `- A1 [not checked] criterion`. Declare a known check on the same line as ` | check: test <exact command and scenario>` or ` | check: source <path:range or symbol>`. Work through the rows in order unless a dependency or user instruction changes the order. Read the named implementation and relevant callers even when the work already exists in the diff. Change the same row to `[closed]` only after verifying that exact criterion on the current sources. Append ` | test: exact check => observed result` for behavior, or ` | source: path:range or symbol => established finding` for a static requirement. A completed row must match its declared check; a general suite pass or a neighboring scenario is not evidence. After steering, an approved requirement may change only with an explicit ` | baseline: changed`, which resets that row's evidence and requires its check again. If the behavior is wrong use `[defect]`; if it is unproven leave `[not checked]` and record the exact remaining check or blocker. Never skip a row, substitute a nearby scenario, remove a criterion, or close it because another row or the general suite passed.

For new or changed behavior, make the first implementation step a test. State the observable outcome, fixture, exact command and expected failure before editing production code; run it on the old behavior and record the actual failure. Apply the smallest contract change, rerun the same test without weakening it, then the nearest existing tests. A test that was already green is compatibility coverage, not a reproduction. Treat an import error, an unprepared fixture or a typo as a setup fault, not Red. Documentation, analysis and mechanical refactors without behavior change use structural checks or already-green tests, never an artificial Red. Record the phase, test path, command and observed result in the same checkpoint, so a compaction after Red resumes at Green while changed sources first rerun that test. Keep that Red → Green checkpoint only when behavior changed and continuation is still needed; a completed check or a static task does not need it. A claim of "done" without the relevant test run is not Green.

Before calling implementation or review complete, reconcile the original plan against its acceptance rows line by line, including every explicit check. All required rows must be `closed` with their own evidence. A remaining `defect` or `not checked` is the next action; if blocked, report it without claiming completion. For a managed implementation, complete the client verification step while the plan still exists. On post-fix review use the same rows on the identified diff; report new findings separately and distinguish targeted verification from a full plan review. After interruption, continue the first unresolved row; reopen a closed row only if its inputs changed or evidence contradicts it.

Use the existing task plan file as the single durable source of the objective, decisions, checkpoint, acceptance criteria and remaining steps. Keep a short checkpoint at its beginning: phase, current unfinished step, authorization, verified contracts with source paths/symbols, remaining unknowns and the next edit or check. Update this checkpoint after a completed step or changed decision; do not regenerate the whole plan. Remove completed work from remaining steps, but retain all acceptance rows and the short evidence needed for final reconciliation until completion. Handoff, summary and context cache reference the plan path instead of copying the checkpoint. A ready implementation step must fit a bounded change and its focused verification, not require reading every file for all later steps. On resume, read only the missing checkpoint or current-step section from the plan. A file cache reduces repeated planning and retrieval; reading it still consumes context and does not imply provider prompt caching.

Resolve material open choices before calling a plan ready or starting dependent implementation. Use the client's interactive question tool when available, with 2–3 concrete alternatives per question, the recommended choice first and a short reason or tradeoff. Batch related questions within the tool's limits. Discover its schema; OpenCode calls this tool `question`, not the `ask` agent. A Markdown list of open questions does not replace the interactive call. If the tool is unavailable, ask in chat and state that limitation. Continue independent investigation while awaiting answers; dismissal, silence and a generic “continue” do not select answers. Choose defaults only when the user delegates those choices or the choice is immaterial; record actual answers and any authorized defaults in the plan.

When `context_cache` is available, save only already-observed TokenSave ranges needed for the next step, without a checkpoint copy; the plan holds the checkpoint. Omit `sources` to retain the selection or pass an empty array to clear it. After compaction, restore only the needed ranges; changed files require scoped MCP reads. Call `action=complete` after the whole task and checks finish, before the final response; leave unfinished or blocked tasks intact.

Loading this skill does not itself switch models, clear context or launch another agent. Use only supported client integration and an explicitly configured routing policy for such transitions. When same-session compaction is configured, use handoff to keep the plan path, constraints and evidence; recover applicable instructions and verify the working tree after compaction. Do not treat a summary as proof that skill contents are loaded.

If the client exposes `brief_transition` under its configured policy and this is not already a receiving planning phase, call it with `stage=plan` before substantive work that needs a new brief, then end the turn. In catalog-based clients, search the tool catalog for `brief_transition` and inspect its schema before deciding it is unavailable; absence from the initial tool list is insufficient. In Code Mode, invoke the advertised catalog path inside `execute`, not as a direct tool. Loading this skill or writing a plan does not perform the transition. For an initial task, pass only the objective and constraints; mid-dialogue, pass a compact Handoff with verified facts, authorization, latest steering and the existing plan path. In a receiving planning phase, create the executable plan and call `stage=implement` only when implementation is authorized and material questions are resolved, then end the turn. Pass only the plan path in that Handoff; include the remaining steps only as a fallback if they could not be saved. Analysis-only tasks finish in planning. An implementation phase follows the adequate plan without transferring again; a materially invalidated plan can request a new brief. The integration compacts the same session and preserves its model and variant; never emulate it with shell workers. Client support and configuration: [context automation](../../docs/context-automation.md).
