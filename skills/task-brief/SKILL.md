# task-brief

Load before substantive investigation or implementation when the task needs architectural decisions, module boundaries or contracts, coordinated changes across components, a complex audit, or debugging with uncertain causes, competing hypotheses or an unsuccessful approach. Explicit requests for a brief, plan, task analysis or design comparison also trigger this skill, even without implementation. Judge complexity by uncertainty, dependencies and consequences, not message length, keywords or file count alone.

Skip routine local changes with a known solution, factual explanations, mechanical commands and execution of an adequate existing plan. An ordinary review uses the review workflow; add this skill when it needs an investigation plan or architectural decisions. Reassess when new evidence invalidates the plan, requirements change materially, or diagnosis stalls; continue from recorded decisions instead of restarting the brief on every turn.

Keep small plans in the conversation. When a plan needs a file, use `.opencode/plans/<task-id>.md` under the project root, with a unique task identifier; an explicit user path takes precedence. Reuse the same path across continuation and record it in the handoff. Keep the plan while work is unfinished or blocked. After the task and its checks are complete, delete only this task's temporary plan before the final response; this cleanup is authorized as part of the task. Preserve user-owned plans and other tasks' files. Do not create a root `PLAN.md` or delete an existing root plan without verifying that it is this task's temporary artifact.

Load only the domain and stack skills for the code affected by the plan. In an indexed project inspect it through tokensave-routing: scoped search and small line ranges; use context without code only to locate unfamiliar structure. Without an index use local search and bounded reads. Reuse project decisions. State the goal, boundaries, assumptions, proposed steps and verification, scaled to the task. Ask only about unresolved choices that materially affect the result. Existing user authorization is sufficient to proceed; do not introduce an additional approval gate or implement changes when only analysis was requested. For a design choice, compare the strongest alternatives with evidence. Harness health diagnostics belong to doctor; it complements this workflow when that is the subject of analysis.

Make the plan executable: record relevant paths and contracts, chosen approach and reasons, unresolved hypotheses, ordered steps, acceptance checks and the next action. Separate verified facts from assumptions; a debugging plan starts with evidence and discriminating checks. Preserve user constraints and authorization through continuation.

Use the existing task plan file as the single durable source of the objective, decisions, checkpoint and remaining steps. Keep a short checkpoint at its beginning: phase, current unfinished step, authorization, verified contracts with source paths/symbols, remaining unknowns and the next edit or check. Update this checkpoint after a completed step or changed decision; do not regenerate the whole plan. Remove a verified step from the remaining steps instead of keeping a completed-step log, and keep only contracts and facts later steps still need. Handoff, summary and context cache reference the plan path instead of copying the checkpoint. A ready implementation step must fit a bounded change and its focused verification, not require reading every file for all later steps. On resume, read only the missing checkpoint or current-step section from the plan. A file cache reduces repeated planning and retrieval; reading it still consumes context and does not imply provider prompt caching.

Resolve material open choices before calling a plan ready or starting dependent implementation. Use the client's interactive question tool when available, with 2–3 concrete alternatives per question, the recommended choice first and a short reason or tradeoff. Batch related questions within the tool's limits. Discover its schema; OpenCode calls this tool `question`, not the `ask` agent. A Markdown list of open questions does not replace the interactive call. If the tool is unavailable, ask in chat and state that limitation. Continue independent investigation while awaiting answers; dismissal, silence and a generic “continue” do not select answers. Choose defaults only when the user delegates those choices or the choice is immaterial; record actual answers and any authorized defaults in the plan.

When `context_cache` is available, save only already-observed TokenSave ranges needed for the next step, without a checkpoint copy; the plan holds the checkpoint. Omit `sources` to retain the selection or pass an empty array to clear it. After compaction, restore only the needed ranges; changed files require scoped MCP reads. Call `action=complete` after the whole task and checks finish, before the final response; leave unfinished or blocked tasks intact.

Loading this skill does not itself switch models, clear context or launch another agent. Use only supported client integration and an explicitly configured routing policy for such transitions. When same-session compaction is configured, use handoff to keep the plan path, constraints and evidence; recover applicable instructions and verify the working tree after compaction. Do not treat a summary as proof that skill contents are loaded.

If the client exposes `brief_transition` under its configured policy and this is not already a receiving planning phase, call it with `stage=plan` before substantive work that needs a new brief, then end the turn. In catalog-based clients, search the tool catalog for `brief_transition` and inspect its schema before deciding it is unavailable; absence from the initial tool list is insufficient. In Code Mode, invoke the advertised catalog path inside `execute`, not as a direct tool. Loading this skill or writing a plan does not perform the transition. For an initial task, pass only the objective and constraints; mid-dialogue, pass a compact Handoff with verified facts, authorization, latest steering and the existing plan path. In a receiving planning phase, create the executable plan and call `stage=implement` only when implementation is authorized and material questions are resolved, then end the turn. Include the decisions, answers, remaining steps and exact plan path in that Handoff. Analysis-only tasks finish in planning. An implementation phase follows the adequate plan without transferring again; a materially invalidated plan can request a new brief. The integration compacts the same session and preserves its model and variant; never emulate it with shell workers. Client support and configuration: [context automation](../../docs/context-automation.md).
