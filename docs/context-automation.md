# Автоматическое управление контекстом

`harness-context` — отдельный клиент установленного `codex app-server`. Он владеет
своими потоками; текущие диалоги CLI/IDE/UI не перехватывает. Модель, провайдер,
approval policy и sandbox берутся из обычной конфигурации Codex. Новых разрешений
runner не выдаёт. Интерактивные запросы завершают автоматизацию с диагностикой:
для такой работы нужен обычный клиент Codex.

После `./install.sh --codex`:

```sh
harness-context run /absolute/project /private/objective.txt /private/permissions.txt
harness-context status /absolute/project
harness-context observe /absolute/project /absolute/rollout.jsonl
```

Objective — конкретная задача, permissions — предоставленные пользователем права
и ограничения, например «локальные правки и проверки разрешены; push запрещён».
Не помещайте пароли и токены в эти файлы. Эти два текста сохраняются приватно,
переносятся без расширения прав; project AGENTS.md читает сам Codex. Запуск `run`
означает запуск новой задачи, а не возобновление текущего UI-диалога. Для follow-up
продолжайте исходный диалог либо задайте новый objective с нужным checkpoint.

Автоматизация включена по умолчанию внутри `run`: каждый завершённый ход выдаёт
заменяемый checkpoint до 3000 символов, с решениями, steering, изменёнными путями,
проверками с указанием входов, неопределёнными операциями и следующим действием.
Неопределённые записи/незавершённые операции останавливают runner. Статус completed
явно сообщает модель после проверок; событие Stop само по себе ничего не завершает.
Контроллер проверяет форму/ack, но не может доказать истинность отчёта модели.

На безопасной границе завершённого хода runner вызывает native compaction.
При повторном заполнении контекста после cooldown он сохраняет checkpoint,
выдаёт статус `manual-handoff` и завершает работу с кодом 1 (задача не завершена).
Автоматического переключения нет: один запуск `run` создаёт только один поток.
Нет переписывания rollout, удаления истории и повторов потенциальных записей.

Для ручного продолжения откройте новый диалог Codex и укажите файл `checkpoint.json`
из сообщения runner: попросите прочитать его, сверить состояние проекта и продолжить
задачу с сохранёнными ограничениями. Новый диалог и момент переноса выбираете вы.
`harness-context status /absolute/project` покажет состояние и последний checkpoint.
После остановки lease освобождается; повторный явный `run` запускает новую задачу,
а не переносит предыдущую автоматически.

Последний аргумент `run` — необязательный JSON с инженерной политикой:

```json
{"contextRatio":0.75,"contextTokens":120000,"cooldownTurns":2,"maxTurns":12,"maxMs":1800000}
```

Это ограничения автоматизации, а не цены или лимиты подписки. Решение использует
последний native totalTokens (включая оценку после compaction), его рост и context
window; при отсутствии totalTokens используется input. Cumulative input не считается
текущим размером контекста. Если window неизвестен, применяется contextTokens.
Минимальный прогресс — увеличение completedSteps. Бюджет включает ходы checkpoint,
сжатие и ожидание; отсутствие прогресса, ошибка или исчерпание бюджета
останавливают цикл. Native defaults модели и compaction не перенастраиваются.
Параметры, кроме contextRatio, должны быть положительными целыми числами.
Прежний параметр maxRotations удалён; старые policy-файлы с ним нужно обновить.

Состояние находится в `$XDG_STATE_HOME/harness/context/<project-hash>` (по умолчанию
`~/.local/state`), вне проекта: state.json, checkpoint.json, generation.json,
lease.json и transitions.jsonl (256 KiB + одна ротация). Файлы 0600, каталог 0700.
Checkpoint/state заменяются атомарно, переходы содержат только классы ошибок и
идентификаторы, без сырого tool output. Usage суммируется по разнице cumulative
снимков отдельно для каждого потока. Reasoning не прибавляется к output второй
раз; стоимость и quota остаются неизвестны. `observe` инкрементально читает
token_count из rollout, сохраняет cursor и usage вместе, не смешивает этот источник
с native событиями и не считает token_usage_record повторно. Один проход ограничен
4 MiB; незавершённая строка остаётся на следующий запуск. После замены/усечения
источника usage перестраивается из текущего файла (sourceRebuilt), утраченная
история не выдаётся за измеренную. Oversized строка требует
ручного разбора. Отслеживаются MCP output bytes, классы ошибок и повторные MCP reads;
произвольные shell/plugin reads не распознаются автоматически.

Только в потоках runner MCP proxy использует if_digest для уже доставленного
диапазона TokenSave. Generation/budget передаются настроенным proxy-серверам явными
process-local `-c mcp_servers.NAME.env...`, без изменения config.toml; это работает
и при фильтрации окружения MCP-клиентом. Имя proxy-сервера должно состоять из
латинских букв, цифр, дефиса или подчёркивания.
Ключ включает путь, диапазон, backend, git ref/commit и
поколение; native compaction, fresh thread и наблюдаемый model reroute сбрасывают
удерживаемые digests. При недоступном/повреждённом generation-файле повторные чтения
снова возвращают текст; явный `if_digest` клиента сохраняется.
Повторная загрузка изменённого файла проверяется самим TokenSave. Описания схем,
правила и skills загружаются агентом один раз на поколение по rules/core.md;
для прямого shell/plugin вызова это инструкция, а не перехватывающий guard.

Proxy ограничивает обычный MCP text до 13000 bytes на результат и внутри runner
суммарно за ход, сохраняет UTF-8 и полный приватный артефакт. При исчерпании
бюджета указатель всё равно виден в text; служебные указатели могут превысить
текстовый бюджет. `_meta.harnessFullResult` дублирует путь. `harness_read_result`
получает диапазон или полный исходный ответ (`full=true`) через MCP без усечения.
JSON text, structuredContent, ошибки и изображения проходят целиком. Ошибка
необязательного lifecycle-состояния оставляет только лимит на один результат.
Обычные CLI/IDE Codex и Qwen используют лимит результата и обработку ошибок,
но не автоматический `if_digest` и не общий бюджет хода. Полного проверенного
контракта событий их истории с процессом MCP нет; SessionStart/Stop и время
жизни процесса недостаточны. Наличие PreCompact/PostCompact у Qwen само по себе
не доказывает такую связь, смену модели и все способы замены истории.
Лимиты, приватное хранение и защита свежих артефактов описаны в
[MCP](../mcp/servers.md). Для шумных команд используйте один brief-output.sh вокруг
всего batch: этот runner не перехватывает произвольные shell outputs до истории.
Нельзя обещать жёсткий общий лимит всей истории при прямых shell/plugin вызовах.

Повторы разрешены лишь для явно перечисленных read-only MCP tools при временной
transport-ошибке, максимум два с backoff. Две одинаковые детерминированные ошибки
открывают circuit для тех же нормализованных аргументов: возвращается исходная
ошибка без вызова backend с пояснением временного подавления. Через 30 секунд
допускается пробный вызов; успех или изменение наблюдаемого индекса снимают
защиту. Неизвестные ошибки circuit не открывают. Writes не
повторяются. graph_root для чужого проекта не удаляется. Внутреннюю ошибку Codex
«missing custom-tool output» proxy не исправляет: сохраните call id, проверьте
rollout на парность call/result; используйте новый поток с проверенным checkpoint,
не replay и не удаление истории. Редактированный воспроизводимый пример описан
в `ai-hooks/test/fixtures/context-protocol-reproducer.md`.

Остановка: Ctrl-C или SIGTERM PID из lease.json. При ошибке сохранён
recovery-required, автоматический replay запрещён. После аварии проверьте native
thread, checkpoint, работающие дочерние команды и последствия незавершённых writes;
затем явно выполните `harness-context recover /absolute/project`. Команда откажет
при живом владельце lease и пометит старую задачу blocked. Это не resume: новую
задачу запускают с уточнённым objective/permissions после ручной сверки. Stale lease
автоматически не крадётся, поскольку дочерние инструменты могут оставаться живыми.

Откат runner: перестать использовать harness-context. Общие оптимизации MCP
отключаются отдельно через `HARNESS_MCP_POLICY_FILE`, как описано в MCP.
Удаление только `~/.local/bin/harness-context` убирает команду. Runtime state можно
удалить после остановки и сверки writes; это не очищает активный контекст сервера.
Текущие UI-разговоры, их доверие к hooks и замена окон остаются под контролем UI.

Контракт сверяется с установленной схемой CLI и изолированной проверкой, а не
только документацией: [App Server](https://learn.chatgpt.com/docs/app-server),
[hooks](https://learn.chatgpt.com/docs/hooks),
[non-interactive](https://learn.chatgpt.com/docs/non-interactive-mode).
