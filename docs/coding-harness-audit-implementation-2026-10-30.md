## Проверки и измерения

### Impact-карта и тестовый набор

Карта в `docs/links/` теперь описывает два контракта:

- `CODEX_HOME` связывает установщик, каталог блокировок, документацию и тест пользовательского каталога.
- `project-init.sh` и `ragsave-sync.sh` связывают инициализацию/синхронизацию двух индексов с Codex hooks и тестами их инвариантов.

Проверка `node ai-hooks/bin/check-impact-map.mjs /home/enkeym/harness` завершилась сообщением `карта: docs/links — все ссылки разрешились`.

Полный раннер `/bin/bash -lc 'node --test --test-concurrency=1 ai-hooks/test/test-*.mjs'` прошёл: 10 файлов, 0 ошибок, около 13,4 с. Вызов тестов через обёртку sandbox завершался `spawnSync git EPERM`; штатный предварительно разрешённый раннер завершился успешно. Sandbox не отключался.

Диагностика sandbox: workspace доступен для записи, `.git` смонтирован read-only, поэтому `git add` потребовал штатное разрешение. Локальная правка `tokensave/config.toml` не является настройкой Codex и не меняет границы этой сессии; в `~/.codex/config.toml` sandbox-профиль явно не задан. Официальная документация описывает `.git` как защищённый путь в профиле `:workspace` и рекомендует узкие правила/разрешения для исключений вместо глобального снятия sandbox ([Sandboxing](https://developers.openai.com/codex/sandboxing), [Config basics](https://developers.openai.com/codex/config-basic)). Для повторного запуска тестов использовать точный разрешённый раннер; другие обёртки требуют отдельного разрешения. Постоянные sandbox-настройки не менялись.

### Token Save и RAG Save

В отдельном временном проекте:

1. Token Save нашёл исходные функцию и caller; повторное чтение с тем же digest вернуло `unchanged=true`.
2. После rename `audit_probe_v1` → `audit_probe_v2`, изменения сигнатуры и sync новое имя/сигнатура находились, старое не выдавалось как актуальное. Чтение с прежним digest вернуло новое содержимое и digest.
3. RAG положительно находил известный документ. Отрицательный запрос вернул слабых соседей со score `0.0328` и `0.0161`; это подтверждает, что результат без порога нельзя трактовать как факт.
4. После изменения документа старый текст не находился; после удаления fixture Token Save сообщил 2 удаления, RAG — 2 удаления, поиск не вернул удалённые данные, статус RAG стал `0 files / 0 chunks`.

### Qwen smoke и baseline

После смены прав три раза отправлен один prompt: `Reply with exactly OK and no other text.` Профиль, модель `deepseek-v4-pro`, safe mode и лимиты были одинаковыми; инструментов и изменений файлов не было.

| Запуск | Полное время | TTFT | Input / output tokens | Cached input | API requests |
|---|---:|---:|---:|---:|---:|
| 1 | 4,676 мс | 4,564 мс | 8,296 / 2 | 2,816 | 1 |
| 2 | 1,798 мс | 1,702 мс | 8,324 / 2 | 2,816 | 1 |
| 3 | 1,622 мс | 1,527 мс | 8,324 / 2 | 8,320 | 1 |

Стоимость не вычислялась: тариф в этой проверке не фиксировался. Время и кэш относятся к smoke-запросу, не к редактированию кода.

Первая Qwen coding-сессия завершилась `FatalTurnLimitedError` после 33 вызовов инструментов. В ограниченном повторе было 12 вызовов (9 успешных, 3 неуспешных) за 26,5 с; локальный `node test.js` напечатал `math tests passed`, но проверял только `add`. Поэтому coding-задача отмечена как неуспешная по критерию корректности, несмотря на проход локального теста.

### MCP

В изолированном профиле `qwen mcp list` показывал Token Save/RAG Save отключёнными, Playwright не ответил в пределах 10 секунд. Простой запрос модели всё же завершился. Клиентские конфиги не задают явные timeout/retry для этих серверов. Этого недостаточно, чтобы подтвердить поведение при таймауте вызова инструмента или ложном успехе после ошибки.

### LiteLLM / DeepSeek

LiteLLM установлен только во временное окружение, proxy слушал `127.0.0.1`. Alias `deepseek-main` разрешился в upstream `deepseek/deepseek-v4-pro`, запрос завершился HTTP 200. Запрос с неверным локальным ключом отклонён HTTP 400. Отдельный локальный master key и upstream key не выводились; проверка логов не нашла ключи. Proxy остановлен, временные конфиг, venv и тестовый профиль удалены.

Версия закреплена на `1.106.6`: перед установкой проверены официальные материалы о компрометации `1.107.0` и release `1.106.6` ([разбор инцидента](https://docs.litellm.ai/blog/security-incident-oct-21-2026-attack-chain), [release](https://github.com/BerriAI/litellm/releases/tag/v1.106.6)). Модель и API base сверены с [документацией DeepSeek для LiteLLM](https://docs.litellm.ai/docs/providers/deepseek). Рабочий endpoint не менялся.
