# План: экономия контекста MCP по умолчанию для Codex и Qwen

Дата: 2026-10-31. Статус: этапы 1–4 и 7 реализованы; этапы 5–6 проверены
в пределах доступного lifecycle, тестов и native MCP без запросов к модели.
Фактические результаты и ограничения: [отчёт](mcp-default-efficiency-results.md).

## Цель

Подключать общий MCP proxy при обычном запуске Codex и Qwen Code. Без ручного
задания переменных окружения ограничивать большие текстовые результаты и снижать
повторные обращения к неисправным инструментам. Автоматически подавлять повторную
передачу файлов только при достоверном отслеживании контекста клиента.

Ожидаемый результат: меньше лишнего текста в истории, повторов и задержек при
сохранении возможности получить полный результат. Процент экономии пятичасового
лимита заранее неизвестен; доля кешированного входа не равна экономии подписки.

## Исходное состояние

- `mcp/servers.json` — общий реестр серверов для обоих клиентов.
- TokenSave подключён через `ai-hooks/bin/mcp-proxy.mjs --compact`.
- RAG запускается напрямую через `ai-hooks/bin/mcp-serve.sh`.
- Codex использует catalog proxy для Playwright. `bin/mcp-sync.mjs:syncQwen`
  заменяет его прямым backend: Qwen опрашивает prompts/resources при обнаружении,
  поэтому существующая схема ленивого запуска ему не подходит.
- `mcp-proxy.mjs:prepareCall` включает retries, защиту от повторных ошибок и
  автоматический `if_digest` только при `HARNESS_CONTEXT_GENERATION_FILE`.
- `mcp-proxy.mjs:transform` ограничивает результаты только в том же режиме.
- `ai-hooks/bin/context-state.mjs` уже содержит `boundTextResult`,
  `reserveTextBudget`, `classify` и `safeRead`. Не создавать параллельную реализацию.
- `harness-context` обеспечивает поколение контекста и бюджет хода для собственных
  потоков. Обычные диалоги CLI/IDE он не контролирует.
- В рабочем дереве есть пользовательские изменения, в том числе в затрагиваемых
  файлах. Реализацию накладывать на актуальное содержимое; `vscode/` не менять.

## Решения и границы

1. Наличие generation-файла больше не включает и не выключает proxy целиком.
   Он сообщает дополнительные возможности клиента: поколение контекста и границы
   хода. Базовые оптимизации работают и без него.
2. По умолчанию применяется лимит на один результат MCP. Существующие 13 000 bytes
   взять как исходное значение для измерения, вынести настройку в общий конфиг.
   Это байты UTF-8, не токены и не общий лимит истории.
3. Общий бюджет на ход включать только при надёжном сигнале начала нового хода.
   Нельзя расходовать один вечный бюджет на весь процесс proxy.
4. Обычный stdio MCP сам по себе не доказывает, что клиент сохранил текст в
   контексте. Время жизни процесса, новый запрос, TTL и `initialize` не считать
   доказательством отсутствия compaction.
5. Без подтверждённого lifecycle автоматический `if_digest` выключен. Явный
   `if_digest` от клиента сохраняется; запрос полного чтения должен работать.
6. Не кешировать готовые ответы модели, операции записи и произвольные результаты
   инструментов. Не пытаться переносить KV-кеш между моделями или провайдерами.
7. Новые процессы-агенты, дополнительные модельные запросы и частые фоновые hooks
   для этой задачи не нужны.

## Этап 1. Общая политика и раздельные возможности

Затрагиваемые области: `mcp-proxy.mjs`, `context-state.mjs`, общий конфиг MCP,
`context-runner.mjs` и установщики при необходимости передачи настроек.

- Отделить три функции: ограничение вывода, обработку ошибок, учёт доставленных
  диапазонов. Их включение не должно зависеть от одной общей переменной.
- Хранить лимит результата, ограничение артефактов и параметры повторов в одном
  конфигурационном слое. Не дублировать значения между клиентами и runner.
- Определить безопасные значения по умолчанию и способ временно отключить
  отдельную оптимизацию для диагностики без редактирования кода.
- Сохранить совместимость существующего runner с generation/budget-файлами.
  Пользователь обычного Codex или Qwen не должен задавать эти переменные.
- Ошибка чтения необязательного lifecycle-состояния выключает подавление текста
  и общий бюджет хода; базовый proxy продолжает работать.

## Этап 2. Ограничение результатов по умолчанию

- Переиспользовать `boundTextResult` вне зависимости от наличия generation-файла.
- Сначала ограничивать только обычные текстовые результаты. JSON text,
  `structuredContent`, изображения, другие типы блоков и ошибки передавать целиком.
- Сохранять полный исходный результат в приватный артефакт до сокращения ответа.
  Сохранять существующие поля ответа и `_meta`, корректность UTF-8 и порядок блоков.
- В ответе оставлять видимый путь к полному результату и исходный размер.
  При бюджете хода резервировать место для указателя, чтобы модель не получила
  пустой ответ с единственным указателем в потенциально невидимых метаданных.
- Предусмотреть чтение нужного диапазона артефакта доступным клиенту способом.
  Получение полного результата не должно снова попадать в тот же цикл усечения.
- Проверить доступность пути из реального окружения обоих клиентов. Не считать
  локальный путь proxy автоматически доступным удалённому клиенту.
- При невозможности безопасно сохранить артефакт вернуть исходный результат
  и краткую диагностику в stderr, а не потерять успешный ответ backend.
- Сохранить ограниченное хранение артефактов и приватные права доступа. Учесть
  параллельные proxy и чтение свежих артефактов при очистке.

## Этап 3. Повторы и восстановление после ошибок

- Учёт вызовов и обработку ошибок включить без generation-файла.
- Использовать явный список операций только для чтения. Операции записи,
  смешанные и неизвестные операции автоматически не повторять.
- Переиспользовать существующую классификацию и задержки; объединить дублирующую
  retry-логику там, где контракты совпадают.
- Повторять лишь явно временные транспортные ошибки в пределах общего лимита
  попыток. Ошибки аргументов, доступа и отсутствие индекса не повторять сразу.
- После двух одинаковых подтверждённых нетранспортных ошибок временно открывать
  защиту для точного ключа: backend, проект, инструмент, нормализованные аргументы.
- Срок защиты задать в общем конфиге. После его истечения допускать один пробный
  вызов; успех очищает состояние, повторная ошибка снова включает защиту.
- Не считать неизвестную ошибку автоматически детерминированной. Не удерживать
  ошибку навсегда: индекс, доступ и окружение могут восстановиться извне.
- При достоверно наблюдаемом изменении соответствующего состояния снимать защиту.
  Новые аргументы, другой проект или backend не должны наследовать чужую ошибку.
- Возвращать корректный ответ MCP с исходным классом ошибки и кратким пояснением
  временного подавления. Не подменять ошибку успешным пустым результатом.
- Ограничить память состояния; не писать секреты и исходные результаты в журнал.

Эта защита сокращает обращения к backend. Она сама по себе не устраняет новый
запрос к модели, если модель снова решила вызвать инструмент. Эффект на количество
модельных обращений измерять отдельно.

## Этап 4. Подключение обоих клиентов

- В `mcp/servers.json` провести TokenSave и RAG через общий proxy с сохранением
  текущего `mcp-serve.sh`, выбора проекта и окружения backend.
- Для Codex сохранить проверенный catalog-режим Playwright и ленивый запуск.
- Для Qwen сохранить прямой handshake с backend, но провести его через proxy
  без catalog-режима. Текущий обход proxy заменить обходом только catalog.
- Проверить prompts/resources, уведомления, negotiation версии протокола,
  корректные JSON-RPC id и параллельные запросы.
- Обновить `bin/mcp-sync.mjs` и проверки установщиков. Сохранить пользовательские
  серверы, авторизацию, trust, timeouts, hooks и настройки моделей.
- Проверить повторную установку и `--check`: отсутствие лишних изменений.
  На время установки старые активные процессы могут продолжить прежний режим;
  новая конфигурация должна применяться при новом подключении MCP.

## Этап 5. Безопасный автоматический if_digest

Сначала проверить реальные протоколы и поддерживаемые события установленных
версий Codex и Qwen. До подтверждения контракта не обещать эту функцию в обычных
сессиях и не включать её по TTL.

- Для каждого клиента установить, доступны ли надёжные идентификаторы диалога,
  события compaction, очистки/замены истории и смены модели.
- Если доступны, добавить минимальный адаптер lifecycle. Он автоматически создаёт
  внутреннее состояние, изолирует диалоги и меняет поколение при потере контекста.
  Ручные переменные пользователю не нужны; существующий runner остаётся адаптером.
- Ключ чтения должен различать проект, файл, диапазон/режим, backend, git ref и
  commit, выбранную модель при известной смене и поколение контекста. Проверку
  актуального содержимого продолжает выполнять TokenSave.
- Запоминать digest только для полного результата, переданного без усечения.
  Не считать наличие сохранённого артефакта доставкой его содержимого модели.
- При compaction, новом диалоге, замене истории, смене модели или потере связи
  с lifecycle очищать удерживаемые digests. При сомнении возвращать текст.
- Не распространять автоматическое подавление на RAG/search и другие операции,
  для которых нет отдельного доказанного контракта удержания результатов.

Если один из клиентов не предоставляет нужных событий, завершить для него этапы
1–4, оставить полные повторные чтения и явно отразить ограничение в документации.
Это допустимый итог реализации, а не повод угадывать состояние контекста.

## Этап 6. Проверки и измерение

Перед изменением тестов загрузить `test-conventions`. Использовать существующие
fixtures и расширять текущие проверки вместо параллельного тестового стенда.

- `test-mcp-proxy.mjs` и `test-context-proxy.mjs`: работа без переменных, UTF-8,
  лимит результата, доступный полный артефакт, ошибка его записи, сохранение JSON,
  ошибок и медиа; параллельные ответы и неизменность протокола.
- Проверки ошибок: ограниченное число транспортных повторов, отсутствие повторов
  записи, истечение защиты и успешное восстановление. Время подменять в тесте,
  не использовать реальные длительные ожидания.
- Проверки digest: изменение содержимого, compaction, новая сессия, смена модели,
  неизвестный lifecycle, явный `if_digest`, принудительное чтение и усечённый ответ.
- `test-qwen.mjs`, `test-codex.mjs`, `test-mcp-serve.mjs`: правильная команда proxy,
  Qwen без catalog, сохранение пользовательских настроек и выбор корня проекта.
- Сохранить проверки runner: общий бюджет сбрасывается на новый ход, generation
  сбрасывается после compaction, отсутствие файлов не ломает обычную сессию.
- После runtime-изменений выполнить требуемый проектом набор:
  `node --test --test-concurrency=1 ai-hooks/test/test-*.mjs`.
- Выполнить `./install.sh --check` и `./install.sh --qwen --check` после синхронизации
  конфигурации. Эти проверки не доказывают фактическое исполнение lifecycle hooks.
- Проверить реальные сценарии в новых сессиях обоих клиентов: малое чтение,
  большой текст, получение артефакта, повтор чтения, ошибка и восстановление.

На фиксированном наборе сопоставимых задач записать до/после: байты результатов
backend и текста модели, число вызовов backend и модели, ошибки, успешность задач,
время, native input/cached input/output/reasoning при наличии валидных счётчиков.
Синтетические проверки отделять от задач с моделью. Уменьшение байтов не называть
экономией токенов; API-стоимость не переводить в расход подписки без основания.

## Этап 7. Документация и завершение

- Обновить `docs/codex.md`, `docs/qwen.md`, `docs/context-automation.md`,
  `mcp/servers.md` и существующую карту связей `docs/links/mcp.md`.
- Описать режим по умолчанию, получение полного результата, исключения из лимита,
  параметры диагностики и фактическую поддержку lifecycle каждого клиента.
- Различать три эффекта: меньший текст в истории, меньше локальной работы backend
  и серверный prompt cache. Не обещать ускорение генерации кешем инструментов.
- Проверить итоговый diff на дублирование, скрытые константы, потерю протокольных
  полей и вмешательство в пользовательские изменения. Комментарии кода не добавлять.

## Критерии готовности

1. Обычные новые сессии Codex и Qwen используют proxy без ручных переменных.
2. Большой обычный текст сокращается; полный результат доступен из клиента.
3. Ошибки, структурированные результаты и медиа сохраняют исходный контракт.
4. Защита от повторных ошибок самостоятельно допускает восстановление backend.
5. Без достоверного lifecycle текст файлов никогда автоматически не подавляется.
6. Существующий `harness-context` сохраняет свои гарантии и ограничения.
7. Тесты проходят; измерения показывают фактический эффект и его пределы.

Рекомендуемый порядок: этапы 1–4, затем проверка возможности этапа 5, проверки,
измерения и документация. Отдельный TTL-кеш поисковых результатов и кеш готовых
ответов модели в этот объём не входят.
