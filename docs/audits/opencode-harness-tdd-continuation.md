## Вывод

Главная правка — **переставить проверку поведения из конца брифа в начало каждого изменения**. `task-brief` требует путей, контрактов и критериев приёмки, но не требует наблюдаемого Red перед production-правкой ([`SKILL.md:14–24`](../../skills/task-brief/SKILL.md#L14-L24)). `test-conventions` уже требует начинать исправление бага с воспроизводящего теста и проверять, что тест способен упасть ([`SKILL.md:15–21`](../../skills/test-conventions/SKILL.md#L15-L21)). Значит, не нужен отдельный навык TDD: в брифе нужно закрепить порядок для нового или изменённого поведения и сделать его видимым при продолжении.

TDD помогает на длинных сессиях, потому что следующий запрос к модели получает проверяемое обязательство, а не только текст о намерениях: видны тест, конкретное падение и команда для перепроверки. Но число тестов само по себе не показатель качества. Мок может зафиксировать неверную гипотезу, зелёный тест — не пройти через реальную границу клиента, а незапущенный тест — вообще не защитить от ошибки. Цель — покрывать различимые исходы и риски, а не перебор всех комбинаций. Не стоит требовать искусственного Red для документации, механического рефакторинга и чистого анализа.

### Три разных «кеша»

1. **План и выборочные исходники.** План на диске хранит текущий шаг; `context_cache` сохраняет только уже виденные нужные диапазоны, привязанные к задаче и проверяемые по хешу. `/handoff` подготавливает кеш до compaction ([`handoff.mjs:88–94`](../../opencode/handoff.mjs#L88-L94)). Валидный диапазон можно восстановить, изменившийся — перечитать. Отсутствие диапазона не повод восстанавливать весь контекст. Даже чтение из локального кеша снова потребляет входные токены.
2. **Дайджест результата MCP и дедупликация проекции.** Прокси единолично подставляет `if_digest` ([`mcp-proxy.mjs:422–424`](../../ai-hooks/bin/mcp-proxy.mjs#L422-L424)); это экономия передачи одинакового результата, не подтверждение, что модель после compaction держит его текст. Не переносить владельца дайджеста в guard. Живое поведение на переключении ветки/worktree оставалось отложено в прошлом аудите.
3. **Провайдерский prompt cache.** Та же сессия и модель не гарантируют cache hit: compaction меняет вход, часть стабильного префикса может сохраниться; результат зависит от провайдера и учёта usage. [`observations.mjs:30–60,252–275`](../../opencode/observations.mjs#L30-L60) уже хранит модель/variant, вход, output, reasoning, native cost и `finish` в записи шага; счётчики cache-read/write хранятся в usage. Не считать отсутствие данных нулём и не выводить цену из байтов инструментов. Этот аудит **не измерил** рост или падение provider cache hit rate после compaction.

## Порядок реализации: один контракт за раз

Сначала **P0** — сам TDD-бриф и его проверка. Затем **P1** — офлайн-диагностика завершений, без изменения поведения. После неё **P2** — узкие исправления передачи плана и актуальности навыков; **P3** — дедупликация инструкций и сравнение стоимости. Не связывать внедрение брифа с обнаружением исходного хода Qwen или Luna. Если записи исходных ходов недоступны, диагноз этих инцидентов остаётся неизвестным, а не подменяется синтетическим подтверждением.

Для каждого пакета:

1. **Red:** в плане указать наблюдаемый исход, фикстуру, команду и ожидаемое отличие. Добавить только тест; запустить на прежнем поведении. Записать саму причину падения. Ошибка импорта, неподготовленная фикстура или опечатка — не Red.
2. **Green:** внести минимальную правку контракта. Запустить тот же тест без ослабления ожидания, затем ближайшие старые тесты. Если тест уже был зелёным до правки, переклассифицировать его в защиту совместимости, а не объявлять воспроизведением.
3. **Refactor:** убрать дублирующееся представление, только если оно мешает; повторить проверки. Для документации и рефакторинга без изменения поведения — проверки структуры либо уже зелёные тесты. Разрешённое исключение указывать в конкретном шаге, не добавлять глобальный флаг.
4. **Checkpoint:** обновить тот же план: текущий пакет и стадия, путь/имя теста, команда, наблюдаемое падение или результат, ближайшее действие. На compaction в Red следующий шаг — Green, если красное падение уже проверено и исходники не изменились; если состояние дерева изменилось, сначала перепроверить ровно этот тест. При возобновлении в Green/Refactor не повторять уже закрытые пакеты.

### P1. Доказательство причин остановки, затем поведение

**Сначала офлайн.** Для доступной записи исходного сбоя связать идентификаторы сессии, пользовательского хода и шага, provider/model/variant, нативный `finish`, ошибку/отмену, факт включения guard и результат следующего шага. В отдельной колонке — наличие незакрытого контракта в плане **в тот момент**. Использовать `finish`, уже записанный в шаге, а не искать слово `length` в прозе модели. Если событие не экспортируется или нативное значение не известно, поставить «неизвестно», не выводить обрыв из `output ≈ 8192`. Не публиковать транскрипты или конфигурацию провайдера.

```js
test("a menu from the previous user turn does not resolve the current question", () => {
  const turn = lastTurn([
    { type: "user", id: "first" },
    { type: "assistant", content: [{ type: "tool", name: "question" }] },
    { type: "user", id: "second" },
    { type: "assistant", content: [{ type: "text", text: "Какую схему сохранить?" }] },
  ])
  assert.equal(turn.human, "second")
  assert.equal(turn.menu, false)
  assert.equal(turn.text, "Какую схему сохранить?")
})
```

**Приёмка P1:** исходные эпизоды отмечены как подтверждённые только при наличии связанной записи; офлайн-матрица проходит при прежних лимитах. Ожидаемый режим: разрешённая работа продолжается, реальный выбор идёт в меню, конкретный технический блокер сообщается с ближайшим действием. Гарантировать отсутствие всех обрывов нельзя. Не вводить массовый retry, «ответь ещё раз» после любого `stop`, распознавание псевдопрогресса по прозе или автоматическую замену модели.

### P2. Compaction: продолжить с нужного состояния, а не переносить всю историю

**Контракт:** план содержит шаги, решения и Red/Green checkpoint. В начальном переходе достаточно цели, разрешений и неизвестных для создания файла. При наличии готового плана переход владеет фазой и ссылкой, не заменяет `remaining` копией аргумента. Уменьшать структурный дубль, а не просто текущий лимит символов. Для отсутствующего плана оставить отдельный fallback; не создавать молча другой план при ошибке чтения или переноса существующего.

| Red / защитная проверка | Ожидаемый результат и владельцы |
| --- | --- |
| В плане записан Red checkpoint; `stage=implement` получает короткий handoff | `test-brief.mjs`: фаза меняется, текущий шаг и содержимое `remaining` не стираются. Шаблон planning system и описание инструмента согласованы с одним источником. |
| План уже существует, нет плана, план в другом дереве, новое steering во время компактации | `test-brief.mjs`, `test-handoff.mjs`: ссылка, а не текст плана; существующий абсолютный fallback сохраняется; нет второй сессии, повторной доставки, скрытого изменения model/variant и затирания нового решения. Без плана есть минимальное создание или конкретная ошибка по существующему контракту. |
| Тяжёлая сводка при короткой ссылке | Проверить отдельно submitted handoff, нативный summary и resume prompt. Тело плана или секретный sentinel отсутствуют там, где не нужны. Не считать прохождение теста ссылки доказательством компактности нативной сводки. |
| Актуальный кеш, изменённый файл, кеш другого worktree; повторное чтение после compaction | `test-opencode-context-cache.mjs`, `test-brief.mjs`, `test-handoff.mjs`: восстанавливается только валидный диапазон нужной задачи, изменившийся перечитывается, чужой не раскрывается. Убедиться, что подсказка `unchanged` не оставляет модель без текста, если старое тело больше не видно. Последнее проверять на реальной границе прокси/адаптера; не дублировать управление дайджестом. |
| Закрытый `review`; нужный skill без тела; нужный skill с телом; изменённая версия | Проверка resume-инструкции и projection-тест: завершённый skill не восстанавливается; актуальный видимый не загружается снова; при отсутствии/изменении — точечное восстановление применимого навыка. Имена в памяти не должны запрещать восстановление содержимого. |

Пример нового регрессионного утверждения для уже существующей фикстуры перехода в `test-brief.mjs` (имена переменных — значения, полученные из фикстуры):

```js
assert.equal(after.remaining, before.remaining)
assert.match(resume.text, /Task plan:/)
assert.ok(!resume.text.includes(redEvidence))
assert.equal(resume.sessionID, sourceSessionID)
```

В исходной фикстуре `before.remaining` должен быть непустым, `redEvidence` уникальным, а `handoff` отличаться от `before.remaining`; иначе первое утверждение может проверять пустой или тривиальный случай. Проверять видимый текст, а не конкретный способ записи на диск. **Приёмка P2:** значимое состояние переживает compaction, но не переезжает в видимый prompt как копия; восстановление затрагивает только нужный материал; уже зелёные проверки переноса и отмены не ослабевают.

### P3. Убрать дубли и оценивать расходы по данным

**Граница изменения:** одна общая семантика в общих правилах; язык активного клиента и его конкретные схемы — в OpenCode-адаптере; процедура навигации — в `tokensave-routing`. Сохранить краткое требование у встроенных инструментов, если без него в их фактическом контексте теряется безопасный маршрут. `doctor` не загружать из-за слова «аудит»: обычный аудит приложения получает соответствующий рабочий навык, сложный — дополнительно `task-brief`, а проблемы инструментов — `doctor`. `optimize` нужен при явной задаче расходов, а не при каждом использовании MCP. Сначала измерить, что действительно присутствует одновременно: каталог навыков и тело конкретного `SKILL.md` — разные объекты.

| Сценарий | Red / приёмка |
| --- | --- |
| Smoke для собранного system prompt | Расчёт на фактически собранном запросе: общая инструкция не повторяется отдельным блоком; короткая tool-подсказка сохраняет работоспособные аргументы и схему. `test-skill-context.mjs`, `test-retrieval-routing.mjs` и соответствующий тест OpenCode-плагина. |
| Без индекса / актуальный индекс / подтверждённо неисправный индекс | В первом случае локальное чтение без MCP; во втором discovery → status → scoped read без `doctor`; в третьем диагностика по доказанной причине. Не регрессировать в чтение всего файла или повторный sync от одного ложного счётчика. |
| Обычный review / сложный аудит кода / аудит skill routing | Офлайн-таблица ожидаемых навыков и явные контрпримеры. Два навыка допустимы при разных целях; одинаковый обзор в двух названиях — не два повода загрузки. Никакого нового диспетчера по словам. |
| Нет usage / cache read равен нулю / есть cache write; повторный вызов / compaction | `test-opencode-observations.mjs`, `test-opencode-cost-report.mjs`, `test-cache-metrics.mjs`: неизвестное не превращается в 0, нулевой hit учитывается, write не складывается с read как «попадания», reasoning не считается дважды, повторный расход не теряется и не дублируется в отчёте. |

**Базовый замер без оплаты:** сравнить офлайн байты фиксированных системных блоков и количество их появлений, число повторных skill/read-вызовов, долю покрытых результатами usage шагов, размеры handoff/summary/reference по отдельности. Это признаки объёма и повторов, не цена и не токены провайдера.

**Проверка экономии при отдельном разрешении:** для сопоставимого workload фиксировать provider/model/variant, последовательность шагов, дерево и состояние префикса; раздельно смотреть cold/warm и до/после compaction. Суммировать отдельно uncached input, cache read, cache write, output/reasoning по контракту провайдера, native cost и coverage; в неизвестных строках не домысливать цену. Сравнивать затраты на **завершённую** задачу, включая повторы, а не цену одного хода. Не считать сокращение байтов экономией в долларах без usage и не менять `#low`, пороги или модели ради замера. В текущую работу этот replay не входит.
