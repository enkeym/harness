# Аудит OpenCode harness: корень проекта, MCP и стоимость контекста

Дата: 2026-11-20. База: `dev`, `5c87e3af27b1f428a6ed795497aa6b25276a2b53`, `/home/enkeym/harness`. Клиент OpenCode 2.3.2, Node 24.18.0, TokenSave 7.16.0. Это план для отдельной реализации, не разрешение на неё. В аудите не менялись исходники, конфигурация или установленные компоненты.

## Итог

1. **P1 — MCP может бесшумно обслуживать другой Git-репозиторий.** В изолированной проверке оба wrapper-а ушли из вложенного Git-репозитория к индексу родителя. Через симлинк к тому же каталогу TokenSave не нашёл индекс, который находился по прямому пути. Это не дефект активного соединения в корне harness: оба MCP сейчас показывают правильный проект.
2. **P1 — у lifecycle нет единого источника актуального каталога.** После исполнения plugin получает каталог сессии, но запускает sync с каталогом, захваченным на setup. Доказано по коду; эффект реального `session.move` и перепривязка transport на OpenCode 2.3.2 ещё не проверены.
3. **P1 — контроль повторов провоцирует лишние ходы и правки в read-only задачах.** Совет «stop gathering / make the first edit» реально появился на 20-м чтении; отдельная ветка кода на верхнем пороге может убрать инструменты. Это особенно вредно для широкого аудита: счётчик не отличает новый материал от повтора.
4. **P2 — предупреждение `stale_commits` можно получить после успешного sync.** Воспроизведено на одном живом MCP; первопричина в расчёте статуса upstream TokenSave, а не в неправильном cwd или устаревшем процессе. Это сигнал к проверке, не доказательство старого содержимого всех файлов.
5. **P2 — повторное чтение и два уровня ограничения ответа не согласованы.** Plugin подставляет дайджест без учёта другого `graph_root`, но не подставляет его для рекомендуемых диапазонов. Объединённый текст нескольких чтений не распознаётся обработчиком. MCP и `execute` применяют разные лимиты, поэтому удачный пакет способен перейти в сценарий «сохранить артефакт → открыть артефакт».
6. **P2 — накладные расходы налицо, экономия не измерена.** В активной записи есть вспомогательный ход compaction и повторные входы инструментов; полный учёт истории, тарифы и сопоставимый baseline отсутствуют. Не менять модель по умолчанию, размер окна, пороги compaction или лимиты наугад.

## 1. Привязка к проекту и worktree

### Доказательства

- `mcp/servers.json:2–12` запускает индексаторы через `ai-hooks/bin/mcp-proxy.mjs` и `mcp-serve.sh`; Playwright запускается отдельно через extension backend. В установленном глобальном `mcp.servers` нет явных `cwd` и `pool`. [Документация OpenCode](https://opencode.ai/docs/mcp-servers) описывает workspace как cwd по умолчанию и `pool=false` как значение по умолчанию; не следует из этого, что старое MCP-соединение автоматически меняет cwd при перемещении сессии.
- `ai-hooks/bin/mcp-serve.sh:17–37,47–54`: поисковый цикл идёт от логического `$PWD` и `pwd` вверх до `$HOME` или `/`, проверяет `-e`, не знает границу Git worktree. В фикстуре `outer` содержал `.tokensave/tokensave.db` и `.ragsave/rag.db`; `outer/inner` был отдельным Git-репозиторием без индексов. Из `inner/deep` stand-in TokenSave получил `serve -p …/outer`, а stand-in RAGSave запустился с cwd `…/outer`. Из симлинка `alias → outer/inner/deep` TokenSave вернул «индекса нет». Ручной `git rev-parse --show-toplevel` и `ragsave.config.find_project_root` оба определили `…/outer/inner`.
- `ai-hooks/bin/tokensave-sync.sh:10–18` и `ai-hooks/bin/ragsave-sync.sh:29–48`: sync использует физическое `pwd -P`, маркер `-f` и останавливается у Git-корня. `ragsave/ragsave/config.py:247–288` канонизирует путь и в Git тоже ограничивает поиск рабочим корнем; вне Git использует свой набор маркеров. `ragsave/ragsave/server.py:83–90` разрешает неявный cwd и явный `project`. Эти договорённости расходятся у точки входа wrapper-а.
- `opencode/harness.js:41–61,290–298`: startup sync запускается с `context.location.directory`; обработчик завершения уже берёт `source.location.directory`, но передаёт его только в наблюдения. `opencode/evidence-cache.mjs:61–65,91–104` также фиксирует корень на setup; допустимая судьба кеша и плана при move требует отдельной проверки. Upstream TokenSave 7.16.0 [описывает отдельно branch drift в multi-branch режиме](https://github.com/aovestdipaperino/tokensave/blob/v7.16.0/src/tokensave/staleness.rs#L37-L63): нельзя считать открытый backend автоматически привязанным к новой ветке.

### План исправления и контракт

1. В диагностике разделить четыре состояния: неправильный проект, отставание по содержимому, подозрение по commit timestamp и отсутствие покрытия. Для no-op sync сначала сверять в одном правильном worktree `HEAD`, `last_sync_at`, `last_updated`, статус и контрольный файл; не подавлять предупреждение глобально. В Harness до обновления — ограниченная диагностическая ветка с одним повторно используемым результатом, без ручного редактирования БД и принудительного полного sync.
2. Добавить покрытие на `.jsonc`, extensionless wrapper и служебный `.opencode/` в retrieval-фикстуре; документировать `tokensave_read` по известному пути отдельно от поиска по графу. Не выкидывать пользовательские документы или весь `.opencode/`. Сначала измерить 1) лишние результаты; 2) влияние exclude на точечное чтение; 3) поведение после compaction.
3. До оптимизации фоновых запусков замерить counters по каноническому корню: `started`, `skip-no-index`, `lock-busy`, `no-change`, `changed`, `failure`; отдельно время shell старта, sync, warm и первого ответа, без содержимого запросов. Если измерения подтверждают дубли, объединять только однотипные запуски одного worktree и сохранять trailing sync после обновления HEAD/файлов. Не превращать debounce в пропуск последней правки или автоматический init. Если warm выигрывает только после простоя, хранить метрики cold/hot раздельно.

**Приёмка:** новый commit без изменения индексируемого содержимого не вызывает бесконечные повторные sync; реально старый/отключённый индекс различим; `.jsonc` находится через RAG; служебный план можно открыть по пути, но он не загрязняет обычный поиск; серия быстрых событий не теряет последнее обновление. Проверить отказ/прерывание warm, contention двух сессий, переключение HEAD и независимость двух worktree.

## 3. Лишние ходы: guard, дайджесты и длина результата

### План исправления и контракт

1. Ввести измерение `turn finished → observe start/end → settle → compaction end → resumed prompt`, плюс число страниц/файлов и размер инструкций по слоям (без текста сообщений или конфига с секретами). Проверить сценарии с медленным/зависшим API наблюдений и двумя параллельными сессиями. Если критический путь подтверждён, отделить локальную обязательную проверку бюджета от тяжёлой выгрузки/форматирования отчёта; дедуплицировать и объединять работу только по правильному owner. Ошибка телеметрии не должна терять steer или бесконечно задерживать продолжение; бюджетные ограничения не ослаблять молча.
2. Проверить managed-план на анализ-only, работу с авторизованным планом, возобновление после compaction, вопрос с незакрытым выбором и move/worktree. Единственный источник состояния — план; ссылка в steer, минимальная сводка при наличии плана, ограниченные диапазоны в `context_cache`. Для пользовательского постоянного файла не применять TTL managed-планов. Не считать `skill` загруженным только по вызову, а digest — доказательством, что тело сохранилось после compaction. Измерить число повторных чтений до первого осмысленного шага, а не до любой правки.
3. После измерения сравнить один стабильный общий блок правил с нынешними повторениями в tool descriptions, skills и phase prompt. Сохранять межклиентную маршрутизацию, проверку project root и точные схемы, а не просто вырезать инструкции. Разделить регрессии «нужный skill не загружен» и «skill зря загружен снова». Сверить `docs/context-automation.md`, установленные ссылки, active catalog и `install.sh --check`. Пороги, `#low` и текущий выбор модели оставить без изменений, пока сопоставимый workload не обосновывает отдельную настройку.

**Приёмка:** после compaction достигается первый незавершённый шаг без нового планирования и копии плана; read-only не переходит к реализации; вопрос не считается отвеченным от steer; сбой наблюдений не теряет handoff; при выключенных метриках выполнение остаётся корректным. Проверки: `test-brief`, `test-handoff`, `test-opencode-observations`, `test-opencode-cost-report`, `test-question-guard`, `test-skill-context`, `test-retrieval-routing`.

## Очередность реализации и критерий выпуска

1. **Сначала корректность root/lifecycle:** фикстуры и общий контракт выбора дерева, затем live-матрица OpenCode. Это независимый приоритетный пакет с тестами, а не переустановка. Не начинать экономию, пока контрольное чтение может происходить из другого дерева.
2. **Затем диагностика freshness и режим guard:** маленькие раздельные пакеты, с явным различением upstream и локального кода. Новый статус и роутинг guard вначале можно проверить без реальных RAG embeddings, провайдера или личной конфигурации.
3. **Затем scoped retrieval, лимиты и наблюдаемость:** сначала измерительный и регрессионный пакет; отдельный change для каждого подтверждённого узкого места. Для архитектуры reuse искать существующие точки в `mcp-serve`/sync, `mcp-proxy`, `read-results`, `output-bounds`, `plan-store` и наблюдателе, не плодить параллельные стеки. Для изменения контрактов перепроверить `docs/links/mcp.md`, `docs/links/indexing.md`, `docs/links/configuration.md`.
4. **Оптимизацию выпускать только по сопоставимой проверке:** одинаковая задача, дерево, модель/вариант, инструкции и критерий качества; отдельно warm/cold. Записать число уникальных/повторных операций, failed/retry, вызовов артефактов, ходов до результата и p50/p95 инструментов; сверить provider usage с native totals. Сначала синтетический replay без платных вызовов; естественные завершённые сессии использовать только с валидированной ценой и полной оговоркой о покрытии. Без достаточных данных выпускать исправление корректности, а оценку экономии оставить открытой.
5. **Финальный gate:** целевые тесты для каждого пакета, затем штатный `node --test --test-concurrency=1 ai-hooks/test/test-*.mjs`, `bash install.sh --check`, итоговая матрица проектов/веток и отсутствие необоснованных изменений в user config/`vscode/`. Для каждого пакета сохранить способ отката: отдельный commit/изолированная правка; для подтверждения upstream — pin версии или диагностический fallback, а не изменение локальных БД.

## Отдельный сценарий: временный DNS-сбой при OAuth OpenAI

Пользователь сообщил `getaddrinfo EAI_AGAIN auth.openai.com`. Ошибка означает, что системный resolver временно не вернул адрес; это не HTTP-ответ от OAuth и не доказательство истёкшего токена. Последующая проверка `node:dns/promises.lookup` из оболочки аудита разрешила `auth.openai.com` за 95 мс, а контрольный `opencode.ai` — за 52 мс. Сбой не воспроизвёлся в оболочке; resolver дочернего процесса OpenCode в момент ошибки не проверен. Сам факт успешной проверки сейчас не исключает кратковременный отказ VPN, WSL, прокси или DNS. Коммит `2d9b7b3` добавляет повтор только для Qwen OAuth, не для `auth.openai.com`.

1. При повторении снять точное время, операцию (login, refresh, compaction или запрос), процесс-инициатор и `error.code`; из того же окружения процесса проверить `dns.lookup` для OAuth-хоста и контрольного домена. Разделить общий DNS-сбой, сбой одного домена и проблему только в окружении клиента. Если DNS уже работает, повторить исходное действие один раз; не удалять сохранённые учётные данные.
2. Если подтверждён отказ в OpenCode, определить владельца вызова: встроенный OAuth, внешний provider plugin или harness. Если вызов не принадлежит harness, не добавлять второй слой повторов и не менять DNS или секреты: зафиксировать версию клиента и обезличенную диагностику для владельца. Если harness действительно владеет вызовом, добавить ограниченный повтор только для безопасного этапа до отправки запроса при `EAI_AGAIN`, с общим дедлайном и поддержкой отмены. Не переносить Qwen-код в OpenAI до подтверждения одинакового контракта.
3. Проверить без сети и токенов: `EAI_AGAIN → успех`, постоянный `EAI_AGAIN`, отмена, `ENOTFOUND`, HTTP 401 и HTTP 429. DNS-ошибка не должна отображаться как неверные учётные данные; 401 и 429 не должны попадать под DNS-retry. Тестировать устойчивость отдельно от привязки MCP к worktree.
