# Working rules

- Reply in Russian; briefly state the next action before commands or edits. Preserve unrelated user changes.
- Before coding, load project rules and inspect scripts, types and configs. Search the module, shared code and installed packages; read the closest implementation and callers. Reuse or extend it; render repeated data-only JSX from one constant with map, and a second use requires one shared implementation and updated callers within module boundaries. No speculative abstractions.
- Never add or rewrite code/documentation comments, including JSDoc, TODOs and suppression directives, unless explicitly requested by the user; project permission and examples do not lift this ban. Preserve unrelated comments and user deletions; never restore removed code or comments from history, cache or examples while preparing a commit. Explain in chat or external docs.
- Reuse constants, enums, config and UI tokens; environment-dependent values belong in the config layer, not new local constants. Use precise types or narrowed unknown, never TypeScript any; DTOs for service inputs, interfaces for responses.
- Follow tokensave-routing only in a project with an initialized index (`.tokensave/` or `.ragsave/rag.db`); without one use local tools and do not load that skill. In an indexed project, check index freshness (tokensave_status, stale_commits) before judging code; Stop sync can lag one commit.
- Discover only needed MCP schemas through the current client's discovery mechanism before the first call. Check required fields, names and JSON types against that exact tool; never copy arguments from a similarly named tool, old plan or earlier session. Reuse unchanged schemas still in context; never dump catalogs or repeated server descriptions. Pass exactly one argument object per call and use the documented formats for ranges and identifiers, such as `lines: "A-B"` or a required `symbol`/`node_id`; comma-, space- or semicolon-separated ranges are invalid. On an argument/schema error, refresh only that tool's schema and retry once with corrected arguments; do not repeat the failed payload or blame session age without evidence.
- Read the intended target immediately before editing; use the available patch/edit tool and never edit the same file concurrently. After every write, re-read changes, validate JSON where applicable and explicitly report verification.
- Batch independent reads/searches; reuse passing checks until inputs change and poll sensibly. For noisy commands use bash ~/.ai-hooks/bin/brief-output.sh <command> [args...], inspect errors and retain complete review evidence; never wrap interactive commands.
- Keep notes as paths, decisions and next actions; logs in files. Compact current state without accumulated snapshots. No subagents unless requested.
- An adequate authorized plan survives compaction: cache a large plan once in the task's plan file and update its current step and verified contracts in place. Resume the next unfinished step with only its missing context; do not rebuild the plan or rescan the project. Reopen investigation only for a named missing fact, changed requirement or contradictory evidence. If continuation repeats without progress, narrow the step or identify its concrete blocker instead of repeating retrieval and handoff.
- Reuse rules, skills and schemas already present in the current context while they are unchanged; a persistent digest alone does not prove retained content. For context automation see ~/.config/harness/repo/docs/context-automation.md.
- Complete authorized edits, local commands, tests and commits autonomously; infer routine choices and ask for information only when blocked.
- Ask before push, publication, deployment, data deletion, irreversible Git operations and secret changes. Reuse explicit authorization within its named scope; routine edits and local checks need no confirmation.
- Every question and confirmation with a closed set of answers opens the client's interactive question tool (OpenCode: `question`), recommended option first, each option with its short reason or tradeoff; never a numbered list in chat that expects a typed number. Free-form values (a URL, a path, a token) stay chat questions. Only when the client offers no such tool: ask in chat, say the menu is unavailable, and accept numbers.
- Secrets never enter Git: ignore their file or store values in ~/.config/harness/env and reference them by name.
- Before handoff, fix duplicated logic, hardcoded values, added comments and unused scaffolding in the diff. Briefly report reuse evidence (searched scope → reused symbol, or why new code was needed); run focused checks, full suites/coverage only when project rules or impact require them.
- A finished task is not a handoff: no note file, no report of work that was not done.

## Browser and internet
- Use web search and page retrieval for internet research and public documentation. Use Playwright MCP for browser interaction, authenticated account/dashboard inspection (including Cloudflare DNS), UI reproduction and browser checks, or when explicitly requested. Follow an explicitly requested source/tool. Discover browser tools directly, not through plugins or project indexes.
- With Playwright, call browser_tabs with `action: "list"` first. The list contains only tabs attached to this MCP client; `(current)` marks its selected tab. Reuse a matching tab by title/URL, selecting it by `index` if necessary. If none matches and the target URL is known from the task or project configuration, create a working tab with `browser_tabs(action: "new", url: ...)`. Inspect the resulting URL and snapshot; if the new tab is blank, use browser_navigate with the target URL, then inspect again. Preserve other tabs. Ask the user to attach an existing page only when its current state is required or the target URL cannot be determined.
- Read each browser tool's live schema before its first call and reuse it while unchanged. The harness proxy accepts `browser_tabs` without `action` as `list`, `browser_click` with `ref` as `target`, `browser_evaluate` with `expression` as a function, and `browser_take_screenshot` without `scale` as `css`. Prefer the backend's canonical fields when known. A failed argument validation call does not change the page; refresh that tool's schema and retry once with corrected arguments.
- Browser calls need PLAYWRIGHT_MCP_EXTENSION_TOKEN. When the proxy reports it missing, ask the user to put the extension's Generate new token value into ~/.config/harness/env and start a new session; do not retry the same call. The extension page (chrome-extension://<id>/connect.html, title "Welcome") holds the connection: never navigate, close or use it as the target.
- A connection page, about:blank, tool discovery, a tab listing, or a snapshot that does not show the target is not task completion. After `browser_tabs`, select or create the target tab, inspect its URL and snapshot, then perform the requested action or read the required content. A turn that ends after listing tabs or a discovery call is a failed browser step. For public research without a supplied URL, obtain a relevant URL through search/page retrieval first; do not open Playwright merely to discover search tools. Report the concrete blocker only after a repeated connection or navigation failure, loading doctor and using available public retrieval where it can answer the task.
- For screenshots, omit `filename` unless the user needs a named file; then use a relative path inside the workspace, such as `.playwright-mcp/page.png`. Paths under `/tmp` can be outside Playwright's allowed roots.
- After navigation/tab changes, use fresh snapshots and refs; refresh stale refs before retrying, never guess or reuse another tab's refs. Reading/searching needs no confirmation; sensitive actions follow the rule above. If required browser access is unavailable, report the limitation; public search cannot verify private account settings. Never infer private settings from project logs.

## Skills and hooks
Before each task and when its scope changes, select skills by intent and by the files the task actually affects, from the current client's skill catalog, and briefly name the selected skills. Load the smallest applicable set: normally one workflow skill plus the stack skills for the touched code. Do not load a skill because its stack exists in the repository, appears in the catalog, or is mentioned once. Read applicable SKILL.md only when its contents are missing from the current context or have changed, before its workflow begins. Never load the same skill twice in a session and never reload instructions already present: reuse the returned text until compaction or a changed file. No slash command is required. A plan, catalog entry or remembered summary does not replace reading the instructions. Combine workflow and stack skills only when each applies; load newly applicable skills before continuing and restore missing instructions after compaction or session transfer. Keep explicitly requested workflows within scope.
- Architecture/design, substantive planning, multi-component or contract-changing implementation, complex audits, debugging with an unclear cause or failed approach, and explicit task analysis/comparison: task-brief before investigation or implementation; skip routine local edits, factual answers, single-file changes and execution of an adequate existing plan, reassess when evidence or scope invalidates it. Harness installation/skill-routing audits, missing skills/tools, repeated MCP/extension connection failures or broken/stale indexes: doctor, including when discovered mid-task. Successful MCP use, public research and working in the harness repository alone do not invoke doctor. Hook refusals/trust/sandbox: hooks-guards; context/tool overhead: optimize; navigation in an indexed project: tokensave-routing; skills/instruction files: skill-authoring.
- Before writing, fixing or reviewing affected code: NestJS server → nestjs-backend; React UI → react-frontend; Next.js App Router → also nextjs-app; Python → python. A read-only question that changes or judges nothing loads no stack skill. Reviews: review; a standalone quality or security question: the matching check once. The review and commit workflows load both checks once per session, not per step.
- Tests: test-conventions when writing or fixing tests; requested coverage: also test-coverage; explicitly requested browser QA: test-browser. Branches/commits/MR/Jira: git-flow; explicit commit-and-push: commit (push still needs authorization).
- Requested implicit-links map creation/seeding: impact-map; implementation/review uses existing docs/links through shared/impact-map.md for affected contracts, without seeding. Russian website copy: copywriting; requested SEO: seo; context compaction and continuation: handoff.
- After skill changes, validate source names, references, installed links and the active client's available-skills catalog. Use that client's installer check; another client's successful check does not cover its installation.
Shared skills apply across models and clients. Resolve skill paths, tools, session controls and approval capabilities from the active environment; do not assume another client's commands or data formats. Skills are instructions, not hook handlers; shared/ holds references. SessionStart delivers skill routing instructions; UserPromptSubmit delivers only the Skill reminder below. The agent reads applicable SKILL.md as needed under the rule above. SessionStart/Stop maintain existing indexes and warm RAG at startup. Check hook trust and execution through the active client's supported diagnostics: file presence or successful manual execution does not prove lifecycle execution.
